# 验证与测试生命周期

## 按风险选择检查

supervisor用几句话说明本轮改动、可能影响与验证方式，记入现有计划即可，不新增检查账本或全量测试清单。项目明确要求的检查仍需完成，但旧阶段记录不自动成为本轮门槛。

| 变更 | 默认验证范围 |
| --- | --- |
| 文案、布局、普通内容参数 | 受影响页面或代表性操作；无需为可逆低影响改动专门新增自动测试 |
| 单个业务功能 | 正常路径、关键边界与直接关联回归 |
| 存档、事务、随机、收益、公共输入或战斗内核 | 对应故障/精度/守恒检查，加受影响系统回归；有广泛影响时才全量运行 |
| 跨系统贯通、重要里程碑或发布 | 全量回归、端到端流程与必要的实际试玩 |

开发中先检查当前功能，修复后检查受影响部分；不要每个候选都重跑全部测试。扩大检查范围应说明具体影响，不能只因为脚本已经存在或为了增加检查数量。固定矩阵可以批量运行，但应有精度、边界、随机或兼容性等明确目的，不默认穷举所有组合。

## 关键行为与独立检查

按本轮实际使用的机制覆盖，不把未实现系统拉进验收：

- 正常操作能完成，状态、结果与反馈一致。
- 非法操作整笔拒绝，不留下部分扣费、奖励或状态。
- 取消、重复提交、退出重开不会错误修改状态或重复发奖。
- 涉及保存时，失败保留同份结果，重试不重复执行。
- 涉及收益、物品、经验时，核对数量、归属与守恒。

独立数值参照只在能为复杂公式、随机、精度、收益结算或恢复等高风险机制提供额外证据时采用，不按系统名称自动要求；普通界面和简单业务不默认再写一套独立实现。已有参照仍适用且实现未变时引用原证据；行为或关键假设变化后再重验。独立参照、独立人工审核和使用子agent是不同手段，不互相强制连带。

通过标准看预期行为是否实际执行、失败是否为0、是否出现脚本错误或中断，不能只看退出码或汇总检查数。失败先区分业务缺陷、测试过时与环境问题；不能为通过而放宽有效断言。规则确实改变时更新受影响用例并说明依据。

## 测试进入与退出

| 类别 | 放置与收尾 |
| --- | --- |
| 长期回归 | 稳定规则、重要故障修复、公共接口边界，进入正式测试目录 |
| 阶段验证 | 调查、独立参照、兼容或专项样本，放临时位置；验收时决定提炼、归档或删除 |
| 临时诊断 | 打印、调试、一次性数据生成和布局探测，默认不进入正式工程或提交 |

长期保留前应能解释：保护什么行为、失败后是否值得处理、机制变化时能否合理维护。不保留只镜像实现、只检查自身生成文本、重复覆盖已有行为或只绑定临时演练页面的测试。

按稳定功能组织长期测试，避免不断新增长期绑定阶段编号、临时目录和固定演练界面的测试。旧阶段脚本已有重要故障用例时先提炼或迁移，不能因改名而丢失覆盖；不要求每轮重构全部旧测试。

worker交付时简述新增长期测试保护的行为、临时验证的去向，以及本轮使哪些旧测试重复或失效；没有这些变化时无需凑表。supervisor确认保留取舍，并只在本轮范围内安排整理，不自动启动全项目清理。

本轮创建的临时产物、核实已被替代的测试可在授权范围内整理；已有测试、用户文件和历史证据不因年代久、名称含旧阶段或本轮未使用就删除。不确定归属或价值时保留。删除失败按[公共协议](../SKILL.md#删除与清理受阻)停止，不强制、不绕过。

## 最少充分证据

默认保留简短最终结论、对应版本、运行方法和必要日志；重要恢复或故障样本须可重现。优先通过Git提交/差异追溯，普通尝试不要求每轮同时保存整份源码副本、完整补丁、压缩包和重复日志。没有Git或确需离线恢复时保留足够副本，不机械套用多份归档。

难以重现、改变审核决定或涉及数据安全的失败保留必要证据；普通修正可在最终记录概述。已经存在的历史证据不因本规范更新自动清理。汇报聚焦可玩结果、关键验证和未验证范围，批量检查数仅作补充，不能替代机制覆盖说明。
